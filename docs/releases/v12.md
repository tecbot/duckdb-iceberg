# DuckDB 2.0.0 baseline and retained patches

Release v12 targets the official DuckDB `v2.0.0` engine, commit
`d54cbbe3df17e8e5ce68312f483b4155836112aa`. Its Iceberg baseline is
`4c0c0874c48ec82a3e29910554891d04bcc0e988`, the exact revision in
[DuckDB 2.0.0's Iceberg configuration](https://github.com/duckdb/duckdb/blob/v2.0.0/.github/config/extensions/iceberg.cmake).
This contains 30 commits after v11's upstream baseline `de29e30d0`.

The v12 source branch starts at that official Iceberg revision. Its production
diff retains snapshot summary properties, zero-row INSERT snapshots, conditional
catalog request idempotency, and conservative handling of malformed UTF-8 bounds.
The source does not carry separate compaction, manifest merging, commit retry,
manifest cleanup, schema binding, or snapshot reference implementations.
Existing issue branches and v11 tags remain available.

The latest upstream `main` was fetched and inspected. It has already moved its
engine submodule past the official 2.0.0 tag. This release uses the official pin
rather than implicitly targeting another development engine.

## Decision and comparison results

The official comparison used DuckDB 2.0.0 with the signed `osx_arm64` Iceberg
extension `4c0c0874c4`, HTTPFS `77392a7207`, and Avro `345c3f4e82`.
The fork comparison used the same official Python and Go engines with the fork's
loadable extension, as well as the locally compiled engine and C API.

| Behavior | Official 2.0.0 result | v12 decision |
| --- | --- | --- |
| `iceberg_rewrite_data_files()` | Six input files rewritten, 12 rows preserved | Use upstream |
| Manifest merging | Three appends leave two manifests and preserve all rows | Use upstream |
| `commit.retry.*` | A stale append receives 409 and can be restaged when retries are enabled | Use upstream |
| Manifest I/O recovery | All eight failure/recovery cases pass | Use upstream |
| `iceberg_refs()` | `main` resolves to the table's current snapshot | Use upstream |
| Snapshot properties | The session setting is unavailable | Retain fork implementation |
| Zero-row INSERT | No additional snapshot | Retain fork implementation |
| Catalog idempotency | An advertised lifetime does not cause an `Idempotency-Key` header | Retain conditional fork implementation |
| Malformed UTF-8 bounds | Equality, join and materialized CTE return too few rows on the retained fixture | Retain conservative fork implementation |

The UTF-8 comparison uses upstream's `utf8_trunc_bounds` fixture, which contains
`foo`, `bar`, and `baz`. Official 2.0.0 repairs its malformed bounds to strings
beginning with `{"name":"John`. Its unfiltered scan returns all three rows, but
its equality and join filters exclude matching rows without an error. This
fixture does not establish that every bound repaired by upstream is unsafe.
It does establish that the existing fork regression is not covered by 2.0.0.
The fork treats an undecodable optional bound as unknown and reads the file.
New writes continue to truncate bounds at valid UTF-8 boundaries.

Idempotency remains conditional on the catalog's advertised
`idempotency-key-lifetime`. It handles a lost response to a mutation that may
already have committed. A definitive 409 and the subsequent regenerated commit
are separate requests with different keys. Upstream's commit conflict retry
policy does not replace replay protection for an unknown transport outcome.

## Read-then-write concurrency

The three-connection reproduction runs on one DuckDB instance:

1. A transaction reads that row 7 is absent.
2. Another connection inserts row 7 and commits.
3. A third connection reads the new head, refreshing the shared cache.
4. The first transaction inserts row 7 with a `NOT EXISTS` guard.
5. The first transaction commits.

Both official 2.0.0 and v12 send the snapshot from the first read in the first
commit's `assert-ref-snapshot-id`. The catalog rejects that request with 409.
The test inspects the rejected request, not only the SQL result.

With `commit.retry.num-retries=0`, the error reaches the caller and there is one
row 7. With the default retry count, upstream restages the append on the new
head without re-executing its SELECT. The commit succeeds and there are two
rows 7. This is the upstream append retry policy, including on v12. Updating the
engine alone does not provide a caller-visible conflict for this guarded INSERT
with retries enabled. Callers that require that result must disable append
retries and rerun the complete transaction after a conflict.

The upstream commit `51d34e378`, titled "undetected conflicts", changes four
compaction test files. It does not change transaction code and is not part of
the official 2.0.0 Iceberg pin. No concurrency fix is attributed to that title.

## Reproduce the comparison

Use Python 3.14. Run commands from the extension repository root. The C API
checks use only the Python standard library and an isolated temporary REST
catalog. No external service or project-specific configuration is required.

For the official alternative, supply the official DuckDB shared library and
signed extension files for the same version and platform:

```sh
python test/release_baseline.py \
  --duckdb-library /absolute/path/to/libduckdb.dylib \
  --httpfs-extension /absolute/path/to/httpfs.duckdb_extension \
  --avro-extension /absolute/path/to/avro.duckdb_extension \
  --iceberg-extension /absolute/path/to/iceberg.duckdb_extension

python test/catalog_read_base.py \
  --duckdb-library /absolute/path/to/libduckdb.dylib \
  --httpfs-extension /absolute/path/to/httpfs.duckdb_extension \
  --avro-extension /absolute/path/to/avro.duckdb_extension \
  --iceberg-extension /absolute/path/to/iceberg.duckdb_extension
```

Repeat the second command with `--append-retries` to check the restaging result.
`release_baseline.py` reports each observed behavior as a boolean. A false value
is a gap, not a passing correctness check. Add `--expect-fork` for the fork to
require every reported behavior to pass. On Linux use `libduckdb.so`.

For a local fork build with statically linked extensions:

```sh
make reldebug
python test/release_baseline.py \
  --duckdb-library build/reldebug/src/libduckdb.dylib --expect-fork
python test/catalog_read_base.py \
  --duckdb-library build/reldebug/src/libduckdb.dylib
python test/catalog_read_base.py \
  --duckdb-library build/reldebug/src/libduckdb.dylib --append-retries
python test/catalog_idempotency.py --duckdb build/reldebug/duckdb --conflict-retry
python test/manifest_io_errors.py --duckdb-library build/reldebug/src/libduckdb.dylib
make test_mock_native_reldebug
build/reldebug/test/unittest_iceberg_native
make format-check
```

For the same manifest I/O test against official binaries, pass the three explicit
extension paths as in the first command. The idempotency suite's first keyed
mutation assertion fails against the official extension, even if the stub
advertises its lifetime; v12 passes all 27 cases.

The pinned Go test module uses `duckdb-go/v2 v2.20000.0`. Its runner creates its
own isolated HTTP catalog. Supply a directory with canonical extension names:

```sh
(cd test/go_runtime && go mod download)
python test/go_runtime/run.py --extensions /absolute/path/to/official/extensions
python test/go_runtime/run.py --extensions /absolute/path/to/fork/extensions --fork
```

The directory must contain `httpfs.duckdb_extension`, `avro.duckdb_extension`, and
`iceberg.duckdb_extension` for DuckDB 2.0.0. The fork run additionally verifies an
empty INSERT snapshot with its captured properties through the Go driver.

## Local verification

The v12 source passed:

- 488 catalog SQL cases with 99,837 assertions; 53 catalog cases were skipped
  for the configured capabilities. These include the retained properties,
  empty INSERT, schema evolution, references and read-base conflict regressions.
- 10 native catalog protocol cases with 1,088 assertions.
- Two native catalog API cases with 22 assertions.
- Six focused local SQL files with 552 assertions.
- All 27 catalog idempotency HTTP cases, including signed headers, OAuth refresh,
  expiry, partial responses and distinct keys for regenerated 409 requests.
- All eight manifest I/O failure/recovery cases on both alternatives.
- Both read-base modes through the C API and the official Go 2.0.0 runtime.
- The ten-check baseline comparison, with all checks passing for the fork.
- C++ build, Python formatting and `make format-check`.

The mock verifies client behavior and the catalog protocol. It does not replace
interoperability or application end-to-end tests with a deployed REST catalog.
The release workflow separately verifies the physical loadable files on Linux
AMD64, Linux ARM64 and macOS ARM64 before publishing assets. A released tag and
its workflow run are the source for those platform results.
